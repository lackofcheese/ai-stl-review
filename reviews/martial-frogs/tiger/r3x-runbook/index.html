Goal

Use the expiring Meshy balance to measure how six already-generated Tiger concepts reconstruct from a single front image, with three stochastic rolls per concept. The survey should reveal whether model family or prompt length produces consistently better front-derived geometry, and whether any individual roll is useful as a prototype.

Single-image reconstruction leaves the back and most side geometry invented. Accordingly, a handsome r3x mesh is evidence about this shortcut, not proof of turnaround consistency and not an automatic production keeper. The normal path remains r3 turnaround → later multi-view Meshy.

How the round is judged

Each returned STL is pushed to Drive immediately, before inspection. Raw meshes remain unit-neutral: validate components, bounds, watertightness, and obvious degeneracy without pretending their units are millimetres. Render a consistent turntable plus close views of hands, feet, toggles, and sash.

A fresh-context comparative review scores, source by source and across the six arms:

  • frog head/body identity and silhouette;
  • planted feet and usable base contact;
  • four-digit webbed hands, with no talons or fused mitts;
  • pose separation and whether both arms remain readable;
  • tangzhuang, three/four source toggle construction, sash, shorts, and wraps;
  • tail/knot geometry where the source contains it;
  • invented back and side anatomy, called out explicitly rather than inferred from the front match;
  • mesh integrity and fragile or floating parts.

The review page may show all 18 static render sets. Interactive viewers are reserved for survivors if embedding all 18 would exceed the artifact budget; the exact raw STLs remain on Drive. Jawaknight and Dimitri make the final call by rotating shortlisted meshes live. No result here silently supersedes the r3 turnaround winner.

The coordinator performs the atomic 360-credit balance preflight before its first provider POST. Record the emitted run id. Durability mode validates every declared output path before spend, pushes each downloaded mesh's bounded repository-relative directory immediately, and records a task as SUCCEEDED only after that push succeeds. A failed push leaves the local output durably LANDED for recovery rather than repeating provider work.

After an interruption or Drive-sync failure, fix storage and resume the same run in durability mode; never submit a new manifest run to replace in-flight or completed task ids:

python3 tools/meshy_manifest.py resume --run RUN_ID --drive-sync

For a LANDED task, resume retries only the Drive push — no new Meshy create, status poll, or download. Durability mode is persisted on the run, but the explicit resume flag keeps the operator command self-documenting.

In another shell, use status --run RUN_ID to identify newly SUCCEEDED outputs. Only after that durable state, validate and render each new file:

python3 tools/meshy_manifest.py status --run RUN_ID
python3 tools/mesh_validate.py --stl PATH_TO_RAW_STL --units raw \
  --label ARTIFACT_ID --out PATH_TO_VALIDATION_JSON
python3 tools/stl_render.py --stl PATH_TO_RAW_STL \
  --out-dir PATH_TO_RENDER_DIR --stem ARTIFACT_ID --mode turnaround \
  --azimuths 270,0,90,180 --elevation 12

Apply those commands independently as each mesh lands; do not wait for all 18.
